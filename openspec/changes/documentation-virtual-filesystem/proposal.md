# Предложение: документация как виртуальная файловая система

## Проблема

Блок «Документация» показывает плоский список вложений. Документация из репозиториев, архивов и отдельных файлов не складывается в единое дерево, совпадения файлов не разрешаются, а генератор материалов рассчитан на один Markdown-файл. Это мешает работать с документацией как с целостным набором файлов и смешивать локальные материалы с внешними источниками.

## Решение

Представить документацию проекта как расширяемую виртуальную файловую систему с иерархическими путями и адаптерами разных источников. Показывать каталоги и файлы деревом с раскрытием/сворачиванием и добавлением из любой папки. Одиночный файл помещается в выбранный каталог под исходным именем; архив раскрывается в каталог с именем архива без `.zip`, `.tar.gz` или `.tar`. Повторное добавление с совпадающими путями запускает разрешение конфликтов: одинаковое содержимое пропускается, различающееся текстовое содержимое открывается в сравнении/слиянии с выбором пользователя. Бинарные конфликты требуют явного выбора версии.

Внешние источники (Confluence, GitHub Wiki и расширяемые будущие интеграции) получают зарезервированные каталоги корневого уровня (`Confluence/`, `GitHub Wiki/` и т. п.). Пользовательские файлы и каталоги не могут занимать зарезервированные имена. Генерация документации из кода записывает набор файлов и каталогов только в локальную часть виртуальной файловой системы; генерация не изменяет подключённые внешние источники.

## Границы

- В этой работе проектируется и реализуется единое дерево документации и его операции с файлами, архивами и локальной генерацией.
- Подключение конкретных API Confluence/GitHub Wiki остаётся отдельными интеграциями через SPI; виртуальная файловая система заранее поддерживает такие адаптеры.
- Генератор возвращает дерево файлов; конкретный LLM-провайдер и качество генерации остаются ответственностью зарегистрированного генератора.
- User Flow сохраняет текущий сценарий материалов и не включается в дерево документации.
