# Спецификация: материалы проекта

## Добавленные требования

### Требование: добавление материалов

СИСТЕМА ДОЛЖНА позволять добавить к документации и User Flow архив `.zip`/`.tar.gz` или файл Markdown. Каждый материал ДОЛЖЕН иметь стабильный идентификатор и храниться отдельно от содержимого записи проекта; конфигурация проекта хранит только метаданные и ссылку на объект. Пользовательское имя отдельного источника не запрашивается — используется имя файла.

#### Сценарий: добавить Markdown

- **ДАНО** открыта страница проекта
- **КОГДА** пользователь добавляет `.md` в документацию или User Flow
- **ТО** текст загружается в объектное хранилище, а материал появляется в выбранной категории

### Требование: просмотр и обновление Markdown

СИСТЕМА ДОЛЖНА открывать Markdown-материал внутри приложения, показывать его содержимое и позволять изменить и сохранить текст в том же материале. Архивы ДОЛЖНЫ поддерживать замену новой версией.

#### Сценарий: сохранить изменения Markdown

- **ДАНО** Markdown-материал открыт в редакторе
- **КОГДА** пользователь изменяет текст и сохраняет его
- **ТО** обновлённый текст хранится по ссылке этого материала и отображается при повторном открытии

#### Сценарий: заменить архив

- **ДАНО** в категории проекта есть архивный материал
- **КОГДА** пользователь загружает для него новый архив
- **ТО** метаданные материала указывают на новую версию архива

### Требование: объединение Markdown-материалов

СИСТЕМА ДОЛЖНА позволять добавить содержимое другого Markdown-материала к открытому тексту и показать объединённый черновик до сохранения. Объединение НЕ ДОЛЖНО автоматически удалять или перезаписывать источник объединяемого текста.

#### Сценарий: объединить материалы

- **ДАНО** открытый Markdown-материал и другой Markdown-материал проекта
- **КОГДА** пользователь выбирает объединяемый материал
- **ТО** содержимое добавляется к черновику с разделителем, источник остаётся без изменений, а результат можно сохранить в открытый материал

### Требование: генераторы материалов с расширением

Интерфейс ДОЛЖЕН показывать действия генерации документации из кода и User Flow из документации. Генератор ДОЛЖЕН подключаться через расширяемый интерфейс. Пока провайдер не зарегистрирован, система НЕ ДОЛЖНА создавать фиктивный результат и ДОЛЖНА сообщать, что генерация ещё не подключена.

#### Сценарий: генератор пока не подключён

- **ДАНО** пользователь нажимает генерацию, но провайдер отсутствует
- **КОГДА** действие выполняется
- **ТО** пользователь видит локализованное сообщение о недоступности генератора, новый ресурс не создаётся

### Требование: сохранность основной документации при генерации

Будущая реализация генерации документации ДОЛЖНА создавать отдельный материал и НЕ ДОЛЖНА перезаписывать или удалять основную документацию проекта либо другие существующие материалы. Удаление материала допускается только как отдельное явное действие пользователя.

#### Сценарий: сгенерировать дополнительную документацию

- **ДАНО** в проекте уже есть основная документация
- **КОГДА** пользователь запускает генерацию документации из кода
- **ТО** результат сохраняется отдельным материалом, а исходная документация остаётся доступна без изменений

### Требование: удаление материала

СИСТЕМА ДОЛЖНА позволять явно удалить прикреплённый архив или Markdown-файл из проекта. Удаление ДОЛЖНО удалять ссылку материала из проекта и соответствующий объект из хранилища после подтверждения пользователя.

#### Сценарий: удалить файл

- **ДАНО** в категории документации или User Flow есть материал
- **КОГДА** пользователь подтверждает удаление
- **ТО** материал и его объект удалены, а остальные материалы не изменены
