## ADDED Requirements

### Requirement: Прикрепление архива логов к issue

Система ДОЛЖНА принимать `.zip` и `.tar.gz` архивы только для существующего issue. Она ДОЛЖНА проверять расширение, сигнатуру и лимит сжатого размера, сохранять исходный архив как S3-артефакт issue и показывать имя, размер и статус обработки. Загрузка архива НЕ ДОЛЖНА автоматически запускать разбор issue.

#### Scenario: Успешная загрузка

- ДАНО: issue существует, архив имеет поддерживаемый формат и не превышает лимит загрузки
- КОГДА: пользователь прикрепляет архив
- ТОГДА: архив сохраняется как артефакт issue, запускается обработка, а UI показывает состояние вложения

#### Scenario: Недопустимый формат или размер

- ДАНО: расширение/сигнатура не соответствуют `.zip` или `.tar.gz`, либо размер превышает лимит
- КОГДА: пользователь загружает файл
- ТОГДА: API возвращает человекочитаемую ошибку и не создаёт активное вложение

### Requirement: Безопасная обработка архивов логов

Система ДОЛЖНА извлекать архив в ограниченной временной области, проверять небезопасные пути и лимит распакованного размера и индексировать только поддерживаемые текстовые записи. Бинарные файлы, неизвестные форматы и непечатаемые данные НЕ ДОЛЖНЫ попадать в embedding или prompt. Декодер ДОЛЖЕН поддерживать UTF-8 (с BOM и без), UTF-16 LE/BE с BOM, Windows-1251 и Windows-1252; выбранная кодировка ДОЛЖНА сохраняться в метаданных фрагмента. Парсер ДОЛЖЕН сохранять относительный путь и номера строк; временные метки ДОЛЖНЫ сохраняться, когда их удаётся определить.

#### Scenario: Архив содержит текстовые и бинарные файлы

- ДАНО: архив содержит поддерживаемые логи и бинарные файлы
- КОГДА: задача индексации обрабатывает архив
- ТОГДА: индексируются только поддерживаемые текстовые записи, бинарные файлы пропускаются с диагностикой

#### Scenario: Логи сохранены в кодировке Windows

- ДАНО: текстовый лог сохранён в Windows-1251, Windows-1252 или UTF-16 с BOM
- КОГДА: задача индексации декодирует файл
- ТОГДА: текст читается без потери символов, а выбранная кодировка записывается в метаданные фрагмента

#### Scenario: Архив пытается выйти за разрешённый путь или превышает лимит распаковки

- ДАНО: архив содержит traversal-путь, опасную ссылку или чрезмерный распакованный объём
- КОГДА: задача индексации проверяет содержимое
- ТОГДА: обработка безопасно отклоняет такой архив, фиксирует понятную ошибку, а issue не получает готовый индекс

### Requirement: Ticket-scoped гибридный поиск логов

Система ДОЛЖНА индексировать обработанные фрагменты с dense- и lexical-представлениями и искать по ним с обязательным ограничением `source_id` и `ticket_id`. Результаты ДОЛЖНЫ содержать ticket evidence reference, путь, диапазон строк и доступные временные метки. Ticket-log retrieval НЕ ДОЛЖЕН участвовать в проектном поиске без явного ticket scope.

#### Scenario: Поиск по собственным логам issue

- ДАНО: индекс issue готов и запрос соответствует его логам
- КОГДА: ticket-agent ищет evidence по запросу триажа
- ТОГДА: возвращаются релевантные фрагменты этого issue с путями, строками и временными метками, если они доступны

#### Scenario: Изоляция логов соседних issue

- ДАНО: два issue одного проекта имеют разные архивы с одинаково релевантным содержимым
- КОГДА: агент первого issue выполняет поиск
- ТОГДА: ни один результат второго issue не возвращается

### Requirement: Готовность вложения и запуск агента

Система ДОЛЖНА показывать состояния очереди, индексации, готовности и ошибки обработки с возможностью повторить обработку. Ticket-agent ДОЛЖЕН запускаться только если все прикреплённые к issue архивы готовы; новая загрузка НЕ ДОЛЖНА автоматически запускать агента. Повторный запуск ДОЛЖЕН переиспользовать индекс неизменённых архивов.

Загруженный attachment неизменяем: новая загрузка создаёт отдельный attachment с уникальным ключом хранения, а повторная обработка использует тот же исходный архив. Новые chunks ДОЛЖНЫ становиться видимыми только после успешного завершения индексации; сбой повтора не ДОЛЖЕН удалять ранее готовые chunks. Повторная постановка одной задачи worker-а НЕ ДОЛЖНА создавать дубли chunks.

#### Scenario: Запуск до готовности всех вложений

- ДАНО: у issue есть вложение в состоянии queued, processing или failed
- КОГДА: пользователь запускает агентов
- ТОГДА: система возвращает понятный конфликт и предлагает дождаться обработки, повторить обработку ошибочного архива или удалить его

#### Scenario: Повтор обработки после ошибки

- ДАНО: обработка вложения завершилась failed
- КОГДА: пользователь выбирает повтор
- ТОГДА: система повторно ставит обработку вложения в очередь и обновляет статус

### Requirement: Логовые evidence в разборе issue

Ticket-agent ДОЛЖЕН добавлять к проектным evidence только релевантные фрагменты логов текущего issue и передавать модели найденные фрагменты, а не исходный архив. Ответ и эскалация ДОЛЖНЫ ссылаться на evidence. Сигналы ошибок приложения и стека, нехватки диска/памяти, OOM kill, лимитов контейнера, конфигурации и внешних зависимостей ДОЛЖНЫ классифицироваться как наблюдения с привязкой к строкам и времени. Агент ДОЛЖЕН сравнивать жалобу с документированными user flow и ожидаемым поведением продукта. Он НЕ ДОЛЖЕН объявлять проблему дефектом кода без подтверждающих evidence и ДОЛЖЕН корректно сообщать о недостатке данных или ожидаемом поведении без обвинения пользователя.

#### Scenario: В логах обнаружен OOM kill

- ДАНО: фрагменты логов содержат свидетельство OOM kill или достижения лимита памяти
- КОГДА: модель формирует ответ по issue
- ТОГДА: evidence передаётся с указанием источника, а ответ сообщает о вероятной ресурсной причине вместо неподтверждённого дефекта кода

#### Scenario: Логи недостаточны для вывода

- ДАНО: индекс не содержит подтверждающих фрагментов или архив частично не читается
- КОГДА: агент формирует результат
- ТОГДА: агент явно указывает неопределённость и недостающие данные либо эскалирует issue

#### Scenario: Жалоба описывает ожидаемый user flow без наблюдаемого сбоя

- ДАНО: проектная документация подтверждает описанное поведение, а ticket evidence не содержит признаков сбоя
- КОГДА: агент формирует ответ
- ТОГДА: он вежливо объясняет ожидаемое поведение, не называет пользователя виноватым и просит конкретный симптом, необходимый для дальнейшей проверки

## MODIFIED Requirements

### Requirement: Контекст ticket-agent

Ticket-agent ДОЛЖЕН использовать проектные знания и, если они приложены и готовы, scoped evidence из логов текущего issue; исходный архив и полный индекс проекта НЕ ДОЛЖНЫ целиком добавляться в prompt.

#### Scenario: Совместный dossier проекта и issue

- ДАНО: есть готовые проектные индексы и логовый индекс текущего issue
- КОГДА: агент строит контекст решения
- ТОГДА: он объединяет ограниченные проектные и ticket-scoped фрагменты с уникальными evidence IDs и корректными citation references
