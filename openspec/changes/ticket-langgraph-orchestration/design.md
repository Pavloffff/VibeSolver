# Дизайн: LangGraph для конвейера обращений

## Рассмотренные варианты

1. **Оставить последовательный Python use case.** Самый простой путь, но маршруты остаются скрытыми в условных операторах.
2. **Перевести существующие шаги на LangGraph.** Даёт явный StateGraph и условные edges без изменения ответственности узлов и без добавления лишних LLM-вызовов. Выбор пользователя.
3. **Сразу добавить Fix Writer и песочницу.** Это другой крупный этап с отдельной моделью угроз, изоляцией файлов, лимитами и approval; не входит в текущий запрос.

## Поток

```text
START → resolve_models → triage → investigate
                                  ├─ dossier пуст → escalate_empty → END
                                  └─ иначе → resolve
                                               ├─ ответ с валидными citations → answer → END
                                               ├─ ответ без валидных citations → escalate_invalid → END
                                               └─ решение escalate → escalate_model → END
```

`TicketGraphState` передаёт ticket, targets, triage, dossier и resolution. Узлы вызывают существующие методы use case, которые сохраняют шаги и стоимость в `ticket_steps`. Граф компилируется один раз на экземпляр use case и вызывается через `ainvoke`; максимальная глубина исполнения задаётся явно. В граф не кладутся credentials, архивы логов или весь проектный индекс.

## Совместимость

- Сохранить синхронный endpoint `POST /tickets/{id}/run`, preflight проверки, статусы, схемы ответов и порядок шагов trace.
- Исключения без доступной модели восстанавливают прежний статус; остальные ошибки отмечают ticket как failed.
- LangGraph state краткоживущий и не является долговременным хранилищем. Источник аудита — существующий `ticket_steps`.
- Узлы не запускают shell, тесты или сгенерированный код.
- Зафиксированная зависимость `langgraph==1.2.22` распространяется под MIT; `pip-audit` не обнаружил известных уязвимостей.
