# Спецификация: обращения и агентный конвейер

## ADDED Requirements

### Требование: жизненный цикл обращения

СИСТЕМА ДОЛЖНА позволять создавать обращение в проекте (заголовок и описание), перечислять обращения проекта с их статусами и получать детали одного обращения вместе с трассировкой. Статусы обращения ДОЛЖНЫ быть данными реестра, а не закрытым перечислением схемы: `new`, `running`, `answered`, `escalated`, `failed`. Повторный запуск конвейера ДОЛЖЕН допускаться для обращений в статусах `answered`, `escalated`, `failed` и НЕ ДОЛЖЕН — пока обращение выполняется.

#### Сценарий: создать обращение

- **ДАНО** проект существует
- **КОГДА** клиент создаёт обращение с заголовком и описанием
- **ТО** API отвечает 201, обращение получает статус `new` и появляется в списке обращений проекта

#### Сценарий: запуск уже выполняющегося обращения

- **ДАНО** обращение в статусе `running`
- **КОГДА** клиент повторно запускает конвейер
- **ТО** API отвечает 409 без изменения обращения

### Требование: агентный конвейер с трассировкой

СИСТЕМА ДОЛЖНА выполнять конвейер из трёх шагов: **Триаж** (классификация: категория, критичность, поисковые запросы), **Исследователь** (сбор досье по индексам проекта через гибридный поиск), **Решатель** (обоснованный ответ или решение об эскалации). Каждый шаг ДОЛЖЕН записываться в append-only трассировку с входом, выходом, использованной моделью и длительностью; сценарии конвейера НЕ ДОЛЖНЫ удалять или изменять записи предыдущих шагов. Маршрутизация между шагами ДОЛЖНА быть детерминированной; количество итераций конвейера ДОЛЖНО быть ограничено (MVP — один проход). Для конвейера ДОЛЖНА требоваться выбранная для проекта chat-модель (роль `ticket_resolution`); её отсутствие или неготовность ДОЛЖНЫ приводить к понятной ошибке до выполнения шагов. Требуемые индексы ДОЛЖНЫ быть завершены: отсутствие контента для поиска ДОЛЖНО завершаться эскалацией с причиной, а не ошибкой сервера.

#### Сценарий: успешный автоварешенный ответ

- **ДАНО** проект с завершённым индексом кода и выбранной chat-моделью
- **КОГДА** конвейер запущен для обращения
- **ТО** обращение получает статус `answered`, ответ ссылается только на переданные источники, трассировка содержит шаги триажа, исследования и решения

#### Сценарий: эскалация вместо ответа

- **ДАНО** Решатель счёл доказательства недостаточными
- **КОГДА** конвейер завершается
- **ТО** обращение получает статус `escalated`, причина эскалации и собранное досье доступны в деталях обращения

### Требование: обоснованность ответа

Ответ ДОЛЖНА опираться только на фрагменты, найденные Исследователем: цитаты ДОЛЖНА использовать переданные `source_ref`, и НЕ ДОЛЖНА ссылаться на источники вне выданного контекста. Ответы ДОЛЖНА формироваться на русском языке. При невозможности обосновать ответ СИСТЕМА ДОЛЖНА эскалировать, а не выдумывать.

#### Сценарий: отклонённые моделью ссылки

- **ДАНО** Решатель вернул ссылки вне выданного контекста
- **КОГДА** конвейер валидирует выход
- **ТО** некорректные ссылки отбрасываются, а при полном отсутствии валидных ссылок обращение эскалируется

### Требование: выбор модели конвейера проектом

Каталог моделей ДОЛЖЕН расшириться ролью `ticket_resolution` с требуемой возможностью `chat`. Селектор ДОЛЖНА допускать только готовые chat-модели рабочего пространства. Интерфейс обращений ДОЛЖЕН показывать выбранную модель и позволять менять её.

#### Сценарий: выбрать модель конвейера

- **ДАНО** в рабочем пространстве есть готовая chat-модель
- **КОГДА** пользователь выбирает её для проекта в разделе обращений
- **ТО** выбор сохраняется, последующие запуски конвейера используют эту модель
