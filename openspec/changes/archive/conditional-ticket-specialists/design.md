# Граф условной диагностики

Триаж выбирает специалистов для конкретного вопроса. Поиск привязан к проекту и обращению. На простой вопрос по документации отвечает автор решения с исходными фрагментами. При неоднозначности аналитик сценария проверяет ожидаемое поведение, диагност логов привязывает симптомы к строкам журнала, исследователь кода проверяет гипотезу по реализации. Каждый получает только относящиеся к его роли источники. Допускается один дополнительный запрос на специалиста по конкретному пробелу в данных. Число вызовов ограничено. Автор решения видит выводы с проверенными ссылками, основания для сомнений и фрагменты источников.

Для спорного результата предусмотрен один независимый проход ревьюера. Недоказанный вывод ведёт к эскалации с причиной. Узлы появляются в диаграмме и журнале с именем исполнителя, ссылками, результатом и расходом модели. Для сравнения инженер может сохранить профиль с отключёнными специалистами. Существующие сохранённые профили и исторические запуски продолжают открываться.

Проверка интерфейса работает с наблюдением на выбранном тестовом стенде. Достаточные для первого этапа факты — доступное имя и роль элемента, состояние, размер. Для внешнего поиска действуют отдельные разрешения проекта и обращения из существующей спецификации ticket-web-search. Внешние сведения имеют отдельное происхождение. Текст обращения и ответ модели не могут назначать сетевые адреса для браузера. Поведение программы подтверждается внутренними источниками или наблюдением.

Для крупных проектов не требуется сборка или развёртывание приложения. Инженер может снять наблюдение с одного выбранного элемента в уже открытом приложении, проверить JSON и прикрепить его к обращению. Источник такого свидетельства — инженер, время относится к моменту сбора. Профиль со включённой проверкой UI предпочитает вложенное наблюдение, затем пробует настроенную проверку существующего стенда. При отсутствии обоих источников вывод об экране остаётся неподтверждённым.

Основание выбора — условный граф из обсуждения. При последовательном запуске всех специалистов простой вопрос расходует вызовы впустую. Один общий решатель оставляет инженеру мало сведений о том, какие проверки выполнены.
