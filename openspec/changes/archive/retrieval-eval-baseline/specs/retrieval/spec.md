# Спецификация: поиск по индексам и оценка качества

## ADDED Requirements

### Требование: поиск по индексам проекта

СИСТЕМА ДОЛЖНА предоставлять эндпоинт `POST /api/v1/sources/{source_id}/search`, принимающий текст запроса, необязательный список типов индексов (по умолчанию — все завершённые индексы проекта) и `top_k` (1–50, по умолчанию 8). Поиск ДОЛЖЕН быть гибридным: плотный векторный (pgvector) и лексический (tsvector) по чанкам активных прогонов выбранных индексов с объединением рангов через RRF. Ответ ДОЛЖНА содержать чанки с путём, веткой, строками, символом, содержимым, итоговым баллом, типом индекса и ссылкой `source_ref`. Поиск по проекту без завершённых индексов ДОЛЖЕН возвращать понятную ошибку (409), несуществующему проекту — 404.

#### Сценарий: найти код по запросу после индексации

- **ДАНО** проект с завершённым индексом кода
- **КОГДА** клиент отправляет запрос поиска с текстом «где обрабатывается загрузка архива»
- **ТО** ответ содержит до `top_k` чанков, отсортированных по убыванию балла, и каждый чанк указывает файл, строки и символ источника

#### Сценарий: поиск без готовых индексов

- **ДАНО** проект, у которого нет ни одного завершённого индекса
- **КОГДА** клиент отправляет запрос поиска
- **ТО** API возвращает 409 с сообщением о необходимости завершить индексацию

### Требование: опциональный переранкинг результатов

СИСТЕМА ДОЛЖНА поддерживать этап cross-encoder переранкинга как расширяемый порт (реестр адаптеров). При включённом реранке СИСТЕМА ДОЛЖНА отбирать гибридных кандидатов (не менее `max(top_k × 4, 32)`), переранжировать их и возвращать лучшие `top_k` с отдельным полем балла реранка. При не настроенном или недоступном реранкере поиск НЕ ДОЛЖНА падать: ДОЛЖНА возвращаться гибридная выдача, а в метаданных ответа ДОЛЖЕН быть признак применённого реранка. Конфигурация реранкера на первом шаге ДОЛЖНА задаваться переменными окружения (адрес, модель), без изменений модели данных.

#### Сценарий: реранкер недоступен

- **ДАНО** реранк включён, но его сервис не отвечает
- **КОГДА** клиент выполняет поиск
- **ТО** API возвращает гибридные результаты, `meta.rerank_applied` равен false, и диагностика попадает в лог без раскрытия секретов

### Требование: золотой набор и метрики качества поиска

СИСТЕМА ДОЛЖНА хранить золотой набор поисковых запросов в репозитории (`backend/eval/golden/`, формат YAML: запрос, тип индекса, список релевантных путей файлов). Скрипт оценки ДОЛЖЕН прогонять набор через публичный поиск и вычислять `recall@k`, `MRR@k` и `nDCG@k` по типам индексов и агрегированно, сохраняя отчёт в JSON и Markdown. Скрипт ДОЛЖЕН работать офлайн (без вызова LLM) поверх dev-стека и завершаться ненулевым кодом при провале порогов, если пороги заданы.

#### Сценарий: прогон оценки на проекте

- **ДАНО** проект проиндексирован, золотой набор для него существует
- **КОГДА** разработчик запускает скрипт оценки
- **ТО** отчёт содержит метрики по каждому типу индекса и агрегат, а также время и число запросов

#### Сценарий: порог качества не достигнут

- **ДАНО** запуск с порогом `--recall-at-10 0.8` и фактическим recall@10 ниже порога
- **КОГДА** скрипт завершается
- **ТО** код возврата отличен от нуля, отчёт указывает проваленные запросы
