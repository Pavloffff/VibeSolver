# Предложение: базовый поиск по индексам и оценка качества RAG

## Зачем это изменение

1. **Агентному слою тикетов нужен поиск как сервис.** Сейчас гибридный поиск (dense pgvector + lexical tsvector + RRF) существует только как приватная функция генерации материалов (`MaterialGenerationUsecase._retrieve_context`). Агенты триажа и исследования кода не могут им пользоваться — придётся дублировать логику.
2. **Цели проекта неизмеримы.** В `openspec/project.md` заявлен критерий recall@10 ≥ 0.8, но в репозитории нет ни золотого набора запросов, ни скрипта метрик. Без базовой линии невозможно доказать ни качество RAG, ни экономию токенов — а это выбранное киллер-направление продукта.
3. **Осталась нереализованной задача про реранкер.** В изменении `separate-project-indexes` (задача 13) реранкер был запланирован и не сделан. Конвейер «dense + BM25 → RRF → cross-encoder reranker» описан в `docs/rag-and-indexing-guide.md`, но кода rerank-этапа нет.

## Текущее состояние → желаемое

- Сейчас: поиск доступен только внутри генерации материалов; метрик нет; реранка нет.
- Желаемо: публичный `POST /api/v1/sources/{id}/search`; переиспользуемый `RetrievalUsecase`; опциональный rerank-этап через расширяемый порт; золотой набор запросов в репозитории; скрипт оценки `recall@k`, `MRR`, `nDCG@k` с отчётом.

## Что НЕ входит

- Langfuse-обсервабельность — отдельное будущее изменение (требует compose-сервис и SDK-зависимость).
- Автоматический подбор реранкера в UI — реранк на первом шаге настраивается окружением (скрытая работающая возможность, как мультиветочный импорт git).
- LLM-оценка качества (RAGAS) — сначала честные retrieval-метрики; генеративные метрики появятся вместе с агентным MVP.
