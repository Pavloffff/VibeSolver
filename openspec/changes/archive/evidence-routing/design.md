# Решения

1. Сначала выбираются фрагменты журналов текущего обращения. Если профиль разрешает анализ логов, специалист сопоставляет события и фактическую конфигурацию с симптомом. Отсутствие журналов оставляет обычный путь по описанию. Версия или платформа подтверждается только конкретной строкой.
2. Аналитик использует описание, уточнение повторного запуска и наблюдения из журналов. Сценарии и документация помогают сформировать гипотезу. Поиск по коду проверяет её и работает также при пустой документации. Завершённые обращения того же проекта дают аналогии и поисковые подсказки.
3. Если фрагментов кода мало, расследование может дочитать ограниченный участок импортированного исходника по пути и ветке найденного фрагмента. При недоступности снимка или несовпадении содержания старая ссылка не превращается в подтверждение.
4. Автор формулирует ответ по локальным основаниям. Рецензент сопоставляет вывод с журналами, кодом и расхождениями. Для утверждений по документации требуется подтверждение в коде. Аналогия с прежней заявкой или внешний источник самостоятельно подтвердить поведение продукта не могут.
5. При недостатке оснований или отклонении рецензентом и при разрешённом инструменте возможен один веб-поиск. Во внешний запрос передаются только допустимые публичные идентификаторы. После попытки система повторно проверяет локальные основания. Если факта всё ещё не хватает, инженер получает конкретный вопрос и материалы.
6. Граф настроек отражает фактические варианты переходов, в том числе повторную локальную проверку. Отключённые роли соблюдаются. Поиск и повторный анализ ограничены по числу проходов и объёму контекста.
