# Дизайн: add-accounts-access

## Решения

- **Авторизация как SPI** (решение пользователя): протокол `Authenticator` + реестр; реализации `noauth-local` и `oauth`. Пароли/OIDC/LDAP позже = новая реализация, ноль изменений кода ресурсов.
- **OAuth — надстройка, а не фундамент** (решение пользователя): внутренние пользователи существуют независимо; `oauth_identities` — таблица связей. Вход через GitHub/GitLab резолвится во внутреннего пользователя. Чисто внутреннее использование остаётся полноценным сценарием.
- **Провайдеры — записи реестра**: изначально поставляются `github`, `gitlab`; клиентские учётные данные из env (`VIBESOLVER_OAUTH_GITHUB_CLIENT_ID/SECRET`, `VIBESOLVER_OAUTH_GITLAB_*`). Новый провайдер (gitea…) = запись реестра + env, без изменений ядра.
- **Сессии**: короткоживущие подписанные токены (JWT, HS256; секрет из env `VIBESOLVER_SESSION_SECRET`), выдаются после OAuth-callback. Локальный режим: вообще без токенов (noauth-local).
- **Наследование git-ролей** (решение пользователя): проект связан с git-репозиторием; API провайдера опрашивается о роли пользователя в репозитории (GitHub `GET /repos/{owner}/{repo}/collaborators/{user}`; GitLab `GET /projects/{id}/members/{uid}`); уровень доступа определяет реестр маппинга. Отрицательные результаты кешируются на короткое время (TTL из env), чтобы не бомбить API провайдеров.
- **Проекты**: внутренние UUID id; источники получают nullable `project_id` (непривязанные источники остаются валидными — обратная совместимость с текущим потоком импорта).
- **Объём RBAC сейчас**: только суперроль admin + наследование git-ролей (решение пользователя); гранулярные роли — более позднее изменение; уровни доступа хранятся как данные (реестр-маппинг), а не enum-колонки.

## Риски / компромиссы

- Rate limits API провайдеров при проверках ролей → короткий TTL-кеш + немедленное обновление на 403.
- OAuth-секрети клиентов живут в env; локальный режим их никогда не требует.
- Отзыв JWT грубый (короткий TTL вместо deny-списка) — приемлемо для MVP.
