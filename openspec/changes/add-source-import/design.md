# Дизайн: add-source-import

## Контекст

Первое изменение на зелёном поле: структура репозитория + инфраструктура + импорт источников. Слой знаний начинается с хранения сырых файлов; чанкинг/эмбеддинг вне рамок (следующее изменение).

## Решения

- **Монорепо** (по лэйауту официального full-stack-fastapi-template, проверенной сообществом конвенции): `backend/` (единственный Python-пакет `app`), `frontend/web/` (Vite + React + TS strict), `frontend/desktop/` (Electron-обёртка той же веб-сборки), `build/` (общие помощники сборки), корневые `docker-compose.yml` + `.env.example`, корневые сборочные скрипты по платформам `build-windows.ps1` / `build-linux.sh` / `build-mac.sh` (каждый делегирует в `build/`), инструкции по сборке в README. npm-проекты остаются простыми (без nx/turbo); общий UI-код — через локальный пакет, если появится дублирование.
- **Electron** (решение пользователя вместо Tauri/RN): `frontend/desktop` загружает собранный бандл `frontend/web`; одна кодовая база React+TS. Упаковка через `electron-builder` для win/linux/mac, управляется корневыми сборочными скриптами.
- **Connector SPI** в `backend/app/connectors/`: dict-реестр + протокол `BaseConnector`. Git через `dulwich` (чистый Python, без зависимости от git-бинарника) — запасной вариант: subprocess git, если dulwich окажется слишком медленным на больших репозиториях.
- **SeaweedFS**: та же топология, что в проверенном эталонном развёртывании (`chrislusf/seaweedfs:4.17`: master → volume → filer → s3 gateway, порт 8333, конфиг s3.json). S3-клиент: `boto3`, направленный на шлюз.
- **Конвейер импорта стадийный с первого дня** (решение пользователя): протокол `PipelineStage` + `STAGE_REGISTRY` (упорядоченный список: fetch → persist; transforms пока пусты). Будущие стадии чанкинга/эмбеддинга/докстрингов/user-flow регистрируются в тот же конвейер — без переделки воркера. Контракт стадии: `run(snapshot: Iterator[RawItem], ctx: ImportContext) -> ...`, где ctx несёт конфиг источника, сессию БД, s3-клиент.
- **Статус импорта без сложного поллинга**: задача импорта пишет строки статуса в Postgres (таблица `imports`: значения статусов, счётчик прогресса, текст ошибки — обычный TEXT, без DB-enum'ов); API отдаёт последнюю строку. Celery result backend для статуса не используется (устойчивость к рестартам).
- **Реестр самоописываемый**: `GET /api/v1/connectors` открывает реестр коннекторов (ключ типа, флаг ready, схема конфига), так что форма UI генерируется из данных — фронтенд никогда не хардкодит список типов (философия расширяемости).
- **БД**: миграции через **goose** (чистые SQL-миграции в `backend/migrations/`, без Alembic — решение пользователя). Таблицы: `sources`, `imports`, `imported_files`.
- **Локальный режим**: `build/start-local` запускает `docker compose up -d` (корневой `docker-compose.yml`) из шелла десктоп-приложения (с детекцией Docker и понятной ошибкой при его отсутствии). Удалённый режим: просто base URL.
- **Сборочные скрипты**: корневые `build-windows.ps1` / `build-linux.sh` / `build-mac.sh` — полные конвейеры упаковки (docker-образ backend + сборка frontend + electron-builder под ОС хоста), общая логика в `build/`; раздел README «Сборка» документирует необходимые компоненты и использование по ОС.
- **Охрана scope**: это изменение импортирует ТОЛЬКО КОД (git, archive + скелеты svn/hg). Коннектор `local_folder` заменён архивным, поскольку путь на машине пользователя недоступен серверу. Без доков/wiki/Confluence, без user flows, без чанкинга, без эмбеддингов — явно отложено в следующие изменения.

## Риски / компромиссы

- dulwich-клон гигантских репозиториев может быть медленным — приемлемо для MVP; измерим на золотом репозитории.
- Бинарник Electron ~100 МБ — принято пользователем (выбран Electron вместо Tauri).
- Чанкинга пока нет: файлы хранятся сырыми; изменение про retrieval будет потреблять `imported_files`.

## Известные упрощения (MVP)

- **`token_ref` пока не используется при клонировании**: поле валидируется и хранится в конфиге источника, но git-коннектор ещё не применяет его для аутентификации при доступе к приватным репозиториям. API при этом никогда не отдаёт `token_ref` наружу (конфиг в ответах санитизируется). Поддержка аутентификации по токену — отдельное будущее изменение.
- **Семантика паттернов `.gitignore` упрощена до сопоставления по имени файла**: без учёта путей, директорий и негативных паттернов (`!...`). Это осознанное упрощение MVP; полная семантика gitignore — кандидат на доработку в одном из следующих изменений.
