# Проектирование генерации по индексам

## Текущее состояние

Frontend содержит `materialGeneratorRegistry`, но реализация генератора в приложении не зарегистрирована. `ProjectPage` ожидает список готовых файлов и сохраняет их через загрузку локальных ресурсов. Индексы хранят чанки, embeddings и `tsvector`; отдельного retrieval API пока нет. Схема User Flow уже валидирует структурированные JSON-сценарии и поддерживает утверждение.

## Целевой поток

1. Backend проверяет готовность требуемых индексов и выбранную чат-модель.
2. Retrieval-компонент ищет релевантные фрагменты только в требуемых типах индекса и актуальных версиях проекта.
3. Для документации извлекаются чанки `code`; для User Flow отдельно извлекаются чанки `code` и `documentation`, затем объединяются по рангу с сохранением происхождения.
4. Генератор получает ограниченный контекст с путями/строками кода, разделами документации и идентификаторами run/snapshot, а не полный репозиторий.
5. LLM возвращает строгий структурированный объект с файлами, относительными путями, содержимым и источниками. Сервер валидирует пути, размеры, число файлов, формат и ссылки на источники.
6. Результат документации сохраняется в локальный `documentation`-ресурс. User Flow сохраняется как неподтверждённый структурированный JSON в `user_flow`; пользователь утверждает сценарии отдельно.
7. Изменение ресурсов помечает соответствующий индекс устаревшим; генерация не подменяет индексацию.

## Retrieval и ранжирование

Сначала нужен общий retrieval-слой, который умеет фильтровать по проекту, типу индекса и активной версии. Начальный поисковый контур: dense поиск по pgvector + полнотекстовый BM25/tsvector, затем Reciprocal Rank Fusion; лимит на число контекстных чанков и отдельные квоты для code/documentation. Reranker можно добавить после измерения качества и времени ответа. Вызов поиска для каждого индекса остаётся раздельным, чтобы происхождение не терялось.

## Контракты и контроль генерации

- Запрос: project ID, категория, параметры формата/объёма; модель определяется настройкой проекта.
- Ответ: список файлов (`path`, `content`, `source_refs`) и provenance (model ID, index run IDs, prompt version).
- Генерация документации выдаёт Markdown и может создать несколько файлов/папок.
- Генерация User Flow выдаёт JSON по существующей канонической схеме, `approved=false`.
- Ограничить максимальные файлы/байты, reject абсолютные пути и `..`, не разрешать конфликтовать с внешними источниками.
- Ошибки retrieval, отсутствия контекста, неверной структуры и таймаута модели отображать отдельно; частичный результат не сохранять до полной валидации.

## Модель и приватность

Индексация выполняется выбранной локальной embedding-моделью. Генератор может использовать любую добавленную чат-модель: при удалённом провайдере наружу отправляются только найденные фрагменты текущих индексов в пределах лимита контекста; полный индекс, конфигурация проекта и секреты не передаются.

## Этапы реализации

1. Внутренний retrieval по каждой версии индекса и DTO происхождения.
2. Блоки контекста для code и documentation с dense + full-text поиском и RRF.
3. Backend use case генерации и строгая схема результата.
4. Проверка выбранной модели, индексов, путей, лимитов и ссылок.
5. Запись локальной документации с несколькими файлами и вложенными путями.
6. Запись draft User Flow, утверждение и обновление индекса.
7. UI статусов, просмотр источников и повторная генерация по актуальным индексам.
8. Оценка качества на golden set и метрики citation coverage/unsupported claims.
