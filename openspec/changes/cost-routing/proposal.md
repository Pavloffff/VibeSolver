# Предложение: cost-routing — каскад моделей для конвейера обращений

## Зачем это изменение

Фаза 3 согласованного роадмапа и первый измеримый шаг киллер-направления «экономия токенов». Сейчас конвейер тикетов использует одну chat-модель на все шаги: триаж (простая задача классификации) и решение идут на одной и той же модели. Исследования (FrugalGPT, cascade routing) показывают 40–70% экономии при маршрутизации простых задач на дешёвые модели — чтобы доказать это на нашем продукте, нужны: (1) раздельные модели для шагов, (2) детерминированная маршрутизация по сложности, (3) учёт токенов/стоимости каждого шага, (4) метрика «$/тикет и % автоварешений». Без учёта стоимости любое заявление об экономии — голословно.

## Текущее состояние → желаемое

- Сейчас: одна роль `ticket_resolution`; шлюз LLM возвращает только текст (usage теряется); трассировка хранит длительность, но не токены; метрик тикетов нет.
- Желаемо: роли `ticket_triage` и `ticket_resolution_cheap` (обе опциональны с деградацией к `ticket_resolution`); триаж возвращает `complexity`; при `simple` и выбранной дешёвой модели решатель идёт на неё; шаги фиксируют tokens_in/out и cost_usd (цены из метаданных модели); эндпоинт статистики тикетов проекта + карточка в UI; инструкция эксперимента single vs cascade.

## Что НЕ входит

- Автоподбор моделей и порогов (RL/байес) — данные для этого появятся после накопления трассировок.
- Цены как отдельная таблица БД — на первом шаге используется `workspace_models.metadata.pricing` (OpenRouter уже её отдаёт); модели без цен учитываются в токенах, но не в долларах.
- Ticket memory (амортизация знаний) — фаза 5.
