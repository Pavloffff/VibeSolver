# Спецификация: каскад моделей конвейера обращений

## ADDED Requirements

### Требование: раздельные модели шагов конвейера

Каталог моделей ДОЛЖЕН расшириться ролями `ticket_triage` и `ticket_resolution_cheap` (обе с требуемой возможностью `chat`). Обе роли ДОЛЖНЫ быть необязательными: если роль не выбрана, соответствующий шаг ИСПОЛЬЗУЕТ модель роли `ticket_resolution`. Интерфейс обращений ДОЛЖЕН позволять выбирать модели всех трёх ролей.

#### Сценарий: триаж дешёвой моделью

- **ДАНО** для проекта выбраны `ticket_triage` = дешёвая модель, `ticket_resolution` = сильная
- **КОГДА** конвейер выполняется
- **ТО** шаг триажа идёт через дешёвую модель, шаг решения — через сильную, трассировка фиксирует модель каждого шага

#### Сценарий: роль не выбрана

- **ДАНО** `ticket_triage` не выбран
- **КОГДА** конвейер выполняется
- **ТО** триаж идёт на модели `ticket_resolution`, запуск завершается успешно без дополнительных требований к конфигурации

### Требование: маршрутизация по сложности тикета

Триаж ДОЛЖЕН возвращать оценку сложности `complexity` (`simple` | `standard` | `hard`). Маршрутизация ДОЛЖНА быть детерминированным правилом в коде: если `complexity = simple` И роль `ticket_resolution_cheap` выбрана — решатель выполняется на дешёвой модели; иначе — на модели `ticket_resolution`. Правило ДОЛЖНО отражаться в трассировке шага решения (какая модель и почему).

#### Сценарий: простой тикет идёт на дешёвую модель

- **ДАНО** `ticket_resolution_cheap` выбран, триаж вернул `complexity = simple`
- **КОГДА** выполняется решатель
- **ТО** он идёт на дешёвой модели, в трассировке шага указана причина маршрутизации

#### Сценарий: сложный тикет идёт на сильную модель

- **ДАНО** триаж вернул `complexity = hard`
- **КОГДА** выполняется решатель
- **ТО** он идёт на модели `ticket_resolution` независимо от наличия дешёвой роли

### Требование: учёт токенов и стоимости шагов

Шлюз LLM ДОЛЖЕН возвращать usage (входные/выходные токены) вместе с текстом ответа; конвейер ДОЛЖЕН записывать их в каждый LLM-шаг трассировки. Для моделей с ценами в метаданных (`pricing` с тарифами за токен) СИСТЕМА ДОЛЖНА вычислять и сохранять стоимость шага; для моделей без цен стоимость НЕ вычисляется, токены сохраняются. Существующие потребители шлюза (генерация материалов) НЕ ДОЛЖНЫ измениться.

#### Сценарий: шаг с известными ценами

- **ДАНО** у модели в метаданных есть `pricing`
- **КОГДА** выполняется LLM-шаг
- **ТО** в трассировке сохраняются tokens_in, tokens_out и cost_usd

#### Сценарий: модель без цен

- **ДАНО** у модели нет `pricing` в метаданных
- **КОГДА** выполняется LLM-шаг
- **ТО** токены сохраняются, cost_usd остаётся незаполненным

### Требование: метрики обращений проекта

СИСТЕМА ДОЛЖНА предоставлять статистику обращений проекта: количество по статусам, долю автоварешений (`answered` / завершённые), суммарные и средние токены, суммарную стоимость (по шагам с ценами) и средний $/тикет. Интерфейс обращений ДОЛЖЕН показывать карточку статистики.

#### Сценарий: статистика после серии обращений

- **ДАНО** в проекте есть отвеченные и эскалированные обращения с заполненной трассировкой
- **КОГДА** клиент запрашивает статистику
- **ТО** ответ содержит долю автоварешений, средние токены на тикет и среднюю стоимость тикета
