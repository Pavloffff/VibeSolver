# Спецификация: индексация контекста проекта

## Добавленные требования

### Требование: постоянное хранение входных файлов

СИСТЕМА ДОЛЖНА сохранять байты файлов, предназначенных для индексации, в постоянном S3-совместимом хранилище и хранить в PostgreSQL ссылки и метаданные, достаточные для повторной индексации без повторной загрузки источника. Манифест без содержимого файла НЕ ДОЛЖЕН считаться сохранённым снимком. Снимки и объекты ДОЛЖНЫ иметь хеши содержимого и происхождение.

#### Сценарий: завершить импорт Git-репозитория

- **ДАНО** Git-коннектор получил файлы текущего снимка репозитория
- **КОГДА** импорт завершается
- **ТО** содержимое каждого включённого файла доступно в S3, а PostgreSQL хранит путь, content hash, ссылку на объект и ревизию репозитория

#### Сценарий: повторно построить индекс после удаления временного клона

- **ДАНО** импорт источника завершён, временный клон удалён
- **КОГДА** пользователь запускает повторную индексацию
- **ТО** индексатор читает байты сохранённого снимка и не требует заново клонировать источник

### Требование: независимые индексы

СИСТЕМА ДОЛЖНА предоставлять отдельные процессы, состояния и версии индекса для кода, документации и User Flow. Состояния ДОЛЖНЫ включать как минимум `not_started`, `queued`, `running`, `completed`, `failed`, `stale`. Каждый результат ДОЛЖЕН ссылаться на версию исходных данных и версии парсера/chunker/embedding-модели, использованные при построении. Список типов индексов ДОЛЖЕН быть расширяемым.

#### Сценарий: индексировать три вида контекста независимо

- **ДАНО** импорт кода, файлы документации и утверждённый User Flow доступны проекту
- **КОГДА** оператор запускает индексацию кода, документации и User Flow по отдельности
- **ТО** у каждой операции свой статус, прогресс, ошибка и активная версия

#### Сценарий: новая версия документации не сбрасывает кодовый индекс

- **ДАНО** кодовый индекс актуален, а документация изменилась
- **КОГДА** документационный индекс помечается устаревшим и перестраивается
- **ТО** кодовый индекс остаётся завершённым и доступным

### Требование: tree-sitter для исходного кода

Индексатор кода ДОЛЖЕН разбирать поддерживаемые языки через расширяемый реестр грамматик tree-sitter и создавать фрагменты, привязанные к AST-узлам и диапазонам строк. Метаданные ДОЛЖНЫ позволять определить проект, источник, репозиторий, путь, commit/branch, язык, символ и content hash. Переполнение лимита модели ДОЛЖНО обрабатываться структурным разбиением и ограниченным fallback, а ошибка отдельного файла НЕ ДОЛЖНА прерывать обработку всех остальных файлов.

#### Сценарий: найти функцию в коде

- **ДАНО** snapshot содержит поддерживаемый файл с классом и методом
- **КОГДА** завершена индексация кода
- **ТО** созданные фрагменты сохраняют символы и диапазоны строк, необходимые для ссылки на исходный код

#### Сценарий: парсер не поддерживает язык файла

- **ДАНО** snapshot содержит файл с неизвестной грамматикой
- **КОГДА** индексатор кода обрабатывает снимок
- **ТО** файл обрабатывается зарегистрированным текстовым fallback либо отмечается пропущенным с диагностикой, остальные файлы индексируются

### Требование: отдельный конвейер документации

Индексатор документации ДОЛЖЕН читать файлы из постоянного снимка и выбирать обработчик через расширяемый реестр форматов. Markdown ДОЛЖЕН сохранять структуру заголовков; другие форматы ДОЛЖНЫ обрабатываться зарегистрированными парсерами. Фрагменты ДОЛЖНЫ сохранять ссылку на исходный файл и позицию. Неподдерживаемый формат ДОЛЖЕН отображаться как предупреждение/ошибка обработки и НЕ ДОЛЖЕН учитываться как успешно проиндексированный.

#### Сценарий: индексировать Markdown по структуре

- **ДАНО** Markdown-документ содержит заголовки и вложенные разделы
- **КОГДА** выполняется индексация документации
- **ТО** текстовые фрагменты сохраняют заголовочную иерархию и ссылку на файл

### Требование: отдельный индекс утверждённых User Flow

Индексатор User Flow ДОЛЖЕН строить отдельное поисковое представление по утверждённым версиям сценариев. Индексируемая версия ДОЛЖНА сохранять название, actor, шаги, ожидаемые результаты, компоненты, режимы отказа, checklist, ссылки и provenance. Черновик или изменённый после индексации сценарий НЕ ДОЛЖЕН считаться актуально проиндексированным до одобрения и успешной переиндексации.

#### Сценарий: индексировать утверждённый Flow

- **ДАНО** пользовательский сценарий утверждён
- **КОГДА** выполнена индексация User Flow
- **ТО** отдельный индекс содержит поисковое представление сценария и ссылку на его версию

### Требование: генераторы зависят от актуальных индексов

Генератор документации из кода ДОЛЖЕН быть доступен только при актуальном завершённом индексе кода. Генератор User Flow ДОЛЖЕН быть доступен только при актуальном завершённом индексе документации. Созданные материалы/сценарии ДОЛЖНЫ помечать соответствующий индекс устаревшим до завершения его переиндексации.

#### Сценарий: блокировать генерацию документации до индекса кода

- **ДАНО** индекс кода отсутствует, выполняется или устарел
- **КОГДА** пользователь открывает действие генерации документации из кода
- **ТО** действие недоступно, а UI объясняет, что сначала нужна актуальная индексация кода

#### Сценарий: блокировать генерацию Flow до индексации документации

- **ДАНО** индекс документации отсутствует, выполняется или устарел
- **КОГДА** пользователь открывает действие генерации User Flow
- **ТО** действие недоступно с указанием на необходимость актуальной индексации документации

### Требование: готовность проекта и доступ к Issues

Проект ДОЛЖЕН считаться готовым только после завершения обязательных импортов проекта и успешного построения актуальных индексов кода, документации и User Flow на версиях текущих входных данных. До готовности интерфейс ДОЛЖЕН показывать красный индикатор, пояснять незавершённые этапы и блокировать переход к Issues. Ошибка или устаревшая версия любого обязательного этапа ДОЛЖНА сохранять проект неготовым.

#### Сценарий: проект ещё не готов

- **ДАНО** не завершён один из обязательных импортов или хотя бы один индекс отсутствует, выполняется, упал либо устарел
- **КОГДА** пользователь открывает проект
- **ТО** индикатор готовности красный, Issues недоступны, а список незавершённых этапов видим

#### Сценарий: проект готов

- **ДАНО** обязательные импорты и три индекса завершены на актуальных версиях данных
- **КОГДА** пользователь открывает проект
- **ТО** индикатор готовности зелёный и переход к Issues доступен

### Требование: объяснение User Flow

Интерфейс ДОЛЖЕН объяснять рядом с User Flow, что это пошаговое описание действий пользователя, ожидаемого поведения системы, связанных частей продукта и известных сбоев. Подсказка ДОЛЖНА быть доступна до создания или индексации Flow.

#### Сценарий: открыть блок User Flow

- **ДАНО** пользователь впервые открывает проект
- **КОГДА** он видит блок User Flow
- **ТО** рядом доступно краткое объяснение назначения и примера состава сценария
