# Проектирование трёх индексов проекта

## Что есть сейчас

- `FetchItems` получает файлы Git или архива в памяти воркера; `PersistItems` записывает результат и метаданные `imported_files`.
- Для archive используется `FullCopyStorage`: каждый файл хранится в S3 под content hash.
- Для Git по умолчанию используется `GitReferenceStorage`: в S3 записывается только JSON-манифест; строки `imported_files` указывают на манифест, а не на долговременные объекты файлов. Клон временный. Такой режим не позволяет надёжно строить индекс после завершения импорта.
- Ресурсы Documentation и User Flow загружаются в S3 как отдельные объекты, метаданные пока хранятся в JSONB конфигурации проекта.
- Индексатор, таблицы чанков, embeddings и полнотекстовый поиск ещё не реализованы. UI-индексация — заглушка; переход к Issues не зависит от готовности контекста.

## Снимок и исходные данные

Ввести версионируемый снимок источника. Для каждого файла снимка хранить проект, источник, относительный путь, происхождение, размер, MIME/кодировку при наличии, content hash, object key SeaweedFS и метаданные ревизии (commit, branch, page ID/version для внешних коннекторов). Ключ объекта контентно-адресный и неизменяемый. Таблицы PostgreSQL содержат ссылки, не копии байтов.

Для Git переключить дефолт на постоянную копию объектов (текущий `FullCopyStorage` — начальная реализация) либо развить Git-хранилище так, чтобы каждый blob всё равно был доступен по S3-ключу. Манифест оставлять как описание снимка, но он не заменяет файлы. Перед запуском парсер читает только сохранённый снимок, а не повторно клонирует удалённый репозиторий.

Входы индексов:

- `code`: файлы исходного кода снимка Git/архива;
- `documentation`: текстовые и поддерживаемые документные файлы виртуальной файловой системы;
- `user_flow`: утверждённые структурированные сценарии и версия каждого сценария.

Файл в S3 является сырьём и источником истины. Текст чанка, AST-метаданные и embedding являются производными артефактами и могут быть пересозданы.

## Независимый запуск и состояния

Логический ключ индекса открыт для расширения, начальные значения: `code`, `documentation`, `user_flow`. Для каждого типа вести состояние отдельно: `not_started`, `queued`, `running`, `completed`, `failed`, `stale`. Запись состояния содержит входной snapshot/version, хеш конфигурации парсера и chunker, модель и ревизию embeddings, число файлов/фрагментов, прогресс, ошибку, timestamps и версию построенного индекса.

Публиковать новый индекс атомарно: текущая активная версия остаётся читаемой, пока новая версия не построена целиком; после проверки указатель активной версии меняется одной транзакцией. Ошибка не уничтожает последний успешный индекс, но проект не считается готовым, если его активная версия уже не соответствует текущему снимку. Повторный запуск идемпотентен по сочетанию `content_hash + parser_version + chunker_version + embedding_model_revision`.

## Индекс кода: tree-sitter

Реестр языков сопоставляет расширение/язык с грамматикой tree-sitter и стратегией чанкинга. Начальные узлы — функция, метод, класс/тип и модульные декларации. Каждый чанк получает границы строк, имя символа, иерархию символов, путь, язык, репозиторий, branch/commit, imports/references, docstring и content hash. В текст embedding включается компактный контекст символа и путь, но исходный код сохраняется точно с диапазоном строк.

Большой узел делится сначала по дочерним AST-узлам, затем — по токенному лимиту модели с перекрытием; маленькие соседние декларации можно объединять с сохранением отдельных метаданных символов. Синтаксически повреждённый или неподдерживаемый файл не должен валить весь индекс: применяется зарегистрированный текстовый fallback или файл пропускается с диагностикой. Бинарные и исключённые файлы не чанкуются. Требуются лимиты размера, глубины AST и времени разбора.

## Индекс документации

Отдельный registry выбирает парсер по MIME/формату. Markdown сохраняет заголовочную иерархию; HTML, PDF, DOCX и другие форматы подключаются отдельными адаптерами. Текст очищается от повторяющегося boilerplate, сохраняет заголовки, страницы/якоря и ссылки. Большие разделы режутся по токенам с небольшим overlap; каждый фрагмент ссылается на исходный объект и позицию. Для формата без адаптера показывается понятная причина, а не фиктивно успешная индексация.

## Индекс User Flow

В качестве источника использовать версию утверждённого сценария, а не просто наличие файла в дереве. Каноническая схема включает название, actor, шаги с действием и ожидаемым результатом, компоненты, failure modes, checklist, ссылки на документацию и provenance. Для embeddings строить представление из названия, шагов и режимов отказа; сохранять связи с исходным Flow ID/version. Flow хранится отдельно от code/doc chunks, чтобы сохранять шаги и связи структурно.

## Хранение и поиск

Предпочтительная модель на первом этапе — общая таблица чанков с `index_kind`, `project_id`, `index_version_id`, `source_file_id`, координатами/символом, текстом, `tsvector`, embedding и JSONB-метаданными. Индекс User Flow может оставаться отдельной таблицей, если запросы по шагам/связям требуют структурной схемы. Логические индексы и состояния всегда отдельные, даже если часть данных лежит в общей таблице.

Код, документация и Flow получают отдельные запросы retrieval с фильтром версии/проекта. Для каждого вида выполняется dense search и BM25, объединение результатов — Reciprocal Rank Fusion (RRF), затем bge-reranker пересортировывает ограниченный набор кандидатов. Веса/лимиты для типов контекста задаются конфигурацией запроса, а не смешением индексов на этапе записи. Retrieval по User Flow может первым определить связанные компоненты и сузить следующий поиск по коду/докам; этот сигнал проверяется абляцией.

## Генераторы и готовность проекта

- `Generate docs from code`: доступна после `code=completed` для текущего snapshot. Выходные файлы создаются только в локальной области документации, затем её индекс помечается `stale` и запускается/предлагается повторная индексация документации.
- `Generate User Flow from docs`: доступна после `documentation=completed` для текущей версии файлов. Сценарии остаются черновиками до подтверждения человека; после утверждения индекс User Flow становится `stale` и пересобирается.
- `ProjectReady` = обязательные импорты проекта завершены + активные актуальные версии всех трёх индексов имеют состояние `completed`. UI показывает красный сигнал при любом незавершённом, ошибочном или устаревшем компоненте; Issues disabled. Кнопки генерации имеют точечные причины блокировки.
- Подсказка у User Flow объясняет его роль простыми словами: пошаговый сценарий пользователя, ожидаемое поведение, связанные части продукта и известные сбои.

## Порядок реализации

1. Персистентное хранилище снимков файлов и изменение стратегии Git.
2. Реестр индексаторов/чанкеров/парсеров и модели версий статусов.
3. Независимая code index job с tree-sitter.
4. Documentation parser registry и документационный index job.
5. Схема Flow, утверждение и отдельная Flow index job.
6. Управляющий API, отображение статусов, readiness gate, блокировка Issues и генерационных действий.
7. Retrieval по трём индексам, RRF и rerank.
8. Golden set, оценки retrieval/answer и абляции источников.

## Безопасность и приватность

Загружать объекты только в настроенный S3-бакет; секреты коннекторов не сохранять рядом с материалами и не передавать embedding API. Перед отправкой на облачную модель соблюдать текущую политику de-identification. Ограничивать архивы, размер файла, типы, количество AST-узлов и время парсинга. Все object key и пути проверять на принадлежность проекту; запрос поиска всегда фильтрует tenant/project и активные версии индексов.
