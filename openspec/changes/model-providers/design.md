# Техническое решение

## Общая схема

Бэкенд хранит записи подключений провайдеров и моделей рабочего пространства. Секреты хранятся отдельно от публичных настроек подключений, зашифрованными ключом из конфигурации окружения. API возвращает только признак наличия ключа и безопасные метаданные. Запросы к провайдерам идут с бэкенда, а не из браузера: это исключает CORS-зависимость и не раскрывает ключи фронтенду.

Предусмотреть расширяемый `ProviderRegistry` с операциями, доступными конкретному провайдеру: проверка соединения, получение доступных моделей, определение возможностей, загрузка/отмена загрузки модели (если поддерживается), выполнение chat-запроса и создание embeddings. Не требовать, чтобы каждый провайдер реализовывал все операции.

В каталоге модели хранить стабильный внутренний ID, ID провайдера, внешний model ID, отображаемое имя, набор capability, состояние, доступные метаданные (например, размер, контекст, размерность эмбеддингов, стоимость). Уникальность — `(provider_connection_id, provider_model_id)`. Списки провайдеров, capability и операций остаются открытыми для расширения.

## Поведение провайдеров

### FreeToken

- Настраиваемый базовый URL OpenAI-совместимого API, например `http://host.docker.internal:1920/v1` для API-контейнера Docker Desktop, если FreeToken запущен на Windows-хосте; URL `localhost` внутри контейнера указывает на сам контейнер.
- Необязательный Bearer/API key, если FreeToken запущен с защитой ключом.
- Синхронизация через `GET /v1/models`; внутренний каталог хранит только модели, опубликованные подключённым сервером (например, `gpt-oss-20b` и `qwen-35b`, если они доступны на сервере пользователя). Не добавлять управление процессом FreeToken или скачиванием его весов.
- Документация FreeToken показывает запуск с моделью через `ft serve --model ...` и API обнаружения `/v1/models`; отдельная операция скачивания/запуска модели для этой фичи не закладывается.
- Capability определяется через метаданные, доступные у сервера, и/или безопасный тест соответствующего API. Не предполагать, что каждая chat-модель поддерживает embeddings.

### Ollama

- Настраиваемый адрес Ollama API; локальная установка обычно доступна по `http://localhost:11434` с машины, где запущен API.
- Список локально установленных моделей получать через `GET /api/tags`. Для загрузки пользователь вводит тег модели из библиотеки Ollama (например, `qwen3:8b`); полный публичный каталог не получать через локальный API. Запрос выполнять через нативный `POST /api/pull` с прогрессом и возможностью отмены, рядом дать ссылку на библиотеку Ollama.
- Для определения capability использовать сведения Ollama о модели и проверку поддерживаемой операции. Нативные endpoints Ollama предпочтительны для каталога и загрузки; OpenAI-совместимый `/v1` не покрывает весь API управления моделями.

### OpenRouter

- Фиксированный API base URL `https://openrouter.ai/api/v1`; пользователь вводит API-ключ.
- Chat-модели получать из `GET /models`, embedding-модели из `GET /embeddings/models`; пользователь добавляет выбранные IDs в локальный каталог рабочего пространства.
- Модель остаётся облачной. Система не показывает загрузку весов. Запросы требуют API-ключа и могут тарифицироваться провайдером.
- Показывать capability и данные каталога (в т.ч. стоимость и контекст, если они предоставлены API); фильтровать большой каталог по имени/ID и capability.

## UI и выбор по задаче

- В боковую навигацию добавить «Модели» с хлебными крошками «Рабочее пространство / Модели».
- Страница содержит подключения провайдеров и каталог добавленных моделей. Действия подключения: добавить, проверить, синхронизировать, изменить, удалить. Для Ollama дополнительно — ввести тег модели из библиотеки, загрузить её с прогрессом и отменить загрузку.
- Селектор индексации показывает только добавленные embedding-модели. Для каждой модели желательно показывать провайдера, ID, размерность и локальный/облачный статус.
- Генерация документации из кода получает селектор только из chat-моделей. До появления реального генератора селектор не должен изображать, что генерация выполняется; UI явно сохраняет статус заглушки.
- Рекомендуемые значения по умолчанию — на уровне рабочего пространства; для страницы проекта допускается переопределение модели индексации на проект. Такое переопределение должно сохраняться и показывать, требует ли смена embedding-модели переиндексации.

## Секреты и границы доверия

- Не хранить ключ OpenRouter как обычное поле модели или в `.env` с ручным редактированием пользователем. Добавить серверное хранилище секретов с шифрованием и ключом из окружения; сам ключ никогда не отдаётся в API, логи или frontend state.
- Пока нет пользовательской авторизации, подключённые провайдеры и секреты общие для всех, кто может достучаться до API данного экземпляра. Для многопользовательского публичного сервера сначала нужна авторизация и разграничение прав либо административный режим для страницы моделей.
- URL FreeToken/Ollama являются адресами исходящих серверных HTTP-запросов. Валидировать схему/адрес и ограничить доступ к опасным адресам; учитывать `host.docker.internal` как разрешённый сценарий для локального Docker Desktop.
- Ошибки соединения переводить в понятные сообщения без выдачи ключей и traceback.

## Данные и совместимость индекса

В задаче модели хранить capabilities, а назначение в VibeSolver хранить отдельными ссылками (например, `index_embedding_model_id` и `documentation_chat_model_id`), не встраивать закрытый список provider/model в схему. При создании embedding-индекса сохранять provider/model ID и размерность. Изменение модели не меняет старый индекс молча: оно требует явной переиндексации, а несовпадение размерности проверяется до запуска.
