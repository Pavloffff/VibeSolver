# Дизайн: опциональный веб-поиск для обращений

## Рассмотренные подходы

1. **Только локальный RAG.** Максимальная приватность и минимум кода, но нельзя найти актуальные сведения о внешней зависимости, ОС или облачном сервисе, которых нет в проектных материалах.
2. **Расширяемый HTTP-адаптер с SearXNG первым провайдером.** Простой контролируемый запрос, независимый от конкретной поисковой системы интерфейс, короткий путь до полезной функции. Требует собственной настройки endpoint и обработки внешних результатов.
3. **Сразу MCP-first.** Удобно подключать разные search tools, но добавляет протокол, lifecycle и разрешения для одной операции; сложнее тестировать и контролировать утечки на первом этапе.

**Выбор:** подход 2. Проект настраивает провайдера SearXNG; обращение хранит выключенный по умолчанию флаг `use_web_search`. Это разделяет доступность провайдера и согласие пользователя на внешний поиск. Реестр позволяет позже добавить MCP-адаптер без изменений ticket-agent.

## Поток

1. Оркестратор запускает внутренний retrieval по коду, документации, user flow и логам.
2. Если включён `use_web_search` и внутреннего evidence недостаточно, узкий normalizer формирует поисковую фразу только из error code/signature, имени библиотеки или сервиса, версии и платформы.
3. Перед запросом normalizer удаляет секреты, адреса, локальные пути с именами пользователей, идентификаторы организаций и произвольные строки лога. Сырые вложения и полный текст обращения в провайдер не передаются.
4. SearXNG adapter ограничивает число результатов и время запроса; сбой внешнего поиска не отменяет внутреннее расследование.
5. Результаты маркируются как внешние недоверенные источники (`W1…`), сохраняют title/URL/дату получения и добавляются к dossier с жёстким лимитом контекста.
6. Resolver использует страницы только как дополнительные справочные материалы, не выполняет инструкции из их текста и не выдаёт их за подтверждение поведения конкретного продукта без внутренних источников.

## Данные и API

- Проект хранит конфигурацию доступного провайдера; endpoint и секреты валидируются и хранятся по существующим правилам конфигурации/секретов.
- Ticket хранит булево `use_web_search`, default `false`; UI показывает рядом с обращением checkbox с объяснением, что очищенная сигнатура будет отправлена поисковому провайдеру.
- Ссылки на внешние страницы входят в citations с URL и типом источника `web`; внутренние ссылки `S1…` не меняют формат.
- В trace фиксируется, выполнялся ли внешний поиск, использованный sanitized query и список URL. Сырые строки логов не сохраняются как поисковый запрос.

## Ограничения

- Веб-поиск не является обязательным шагом и не влияет на обращения с выключенным флагом.
- Для системных, ресурсных и пользовательских проблем внешний поиск не запускается автоматически, пока внутренняя диагностика не нашла специфичную поисковую сигнатуру.
- Внешний контент может быть неверным или вредоносным; prompt и валидатор трактуют его как недоверенные данные.
