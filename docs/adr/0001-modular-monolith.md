# ADR-0001: Модульный монолит вместо микросервисов

- Статус: принято
- Дата: 2026-11
- Контекст диплома: см. `openspec/project.md`, C4-диаграммы в `D:\maga\diplom\png\`

## Контекст

VibeSolver — система из двух слоёв (слой знаний, слой обработки обращений) со стеком: FastAPI, Celery, PostgreSQL+pgvector, SeaweedFS, React+TS, LangGraph. Развёртывание MVP — один хост docker-compose. Команда — один разработчик + AI-агенты. Философия проекта: удобство пользователя и расширяемость.

## Решение

Модульный монолит: **две развёртываемые единицы** (API-процесс FastAPI + Celery-воркеры) над общей БД, разделённые на модули с жёсткими внутренними границами:

- `app/connectors/` — SPI источников (реестр коннекторов);
- `app/workers/` — стадийный конвейер импорта (реестр стадий);
- `app/storage/` — клиенты pgvector/SeaweedFS, стратегии хранения (реестр);
- `app/api/` — HTTP-контракты.

Границы модулей проходят по тем же швам, что и будущие сервисные границы (см. ниже). Никакого кода между модулями в обход контрактных типов (Pydantic) нет.

## Почему НЕ микросервисы

1. **Операционная сложность против MVP.** Микросервисы добавляют: сервис-дискавери, распределённые транзакции (saga/outbox), межсервисный трейсинг, версионирование контрактов, сетевые отказы как новый класс ошибок. Для прототипа диплома это недели работы без единицы пользовательской ценности.
2. **Нет выигрыша в масштабировании.** Горизонтальное масштабирование уже доступно там, где оно нужно: Celery-воркеры импорта и агентного конвейера скейлятся репликой контейнера. Узкое место системы — LLM-вызовы (внешние) и retrieval (одна БД) — микросервисами не лечится.
3. **Дублирование инфраструктуры.** Каждый сервис = свой Dockerfile, миграции, конфиг, healthcheck, пайплайн сборки. Для одного разработчика поддержка N сервисов означает N-кратную рутину.
4. **Локальность данных — главное преимущество.** RAG-конвейер (retrieval → rerank → генерация) чувствителен к латентности: общая транзакция «векторный + полнотекстовый поиск + реляции» в PostgreSQL — ключевое обоснование стека. Разнос по сервисам разрушил бы транзакционную целостность и добавил бы сетевые хопы на каждый шаг конвейера.
5. **Мультиагентная часть — это не микросервисы.** Агенты — узлы одного графа LangGraph с общим персистентным состоянием (thread_id = ticket_id). Их «разделение» — это логический граф, а не физические процессы.

## Как остаёмся расширяемыми (мостик к будущему)

Расчёт на «extract-if-needed»: швы модулей спроектированы как явные интерфейсы, за которыми завтра может встать сетевой вызов без переписывания ядра:

| Шов (интерфейс) | Что позволит вынести |
|---|---|
| Connector SPI (`connectors/`) | отдельный ingestion-сервис |
| PipelineStage registry (`workers/`) | отдельные обработчики стадий |
| Storage strategy registry (`storage/`) | S3-стратегии как сервис |
| LLM-шлюз | отдельный прокси-сервис моделей |
| VectorStore интерфейс | замена pgvector → Qdrant без изменения кода |
| OutcomeSink (MR Builder / Escalation) | интеграции (GitLab, Jira, Webhook) |

Правило: модуль может быть «вынесен» в сервис только когда у него появится своя команда или независимый SLA (см. критерии ниже).

## Критерии пересмотра решения

- несколько независимых команд разработки;
- мультитенантность с изоляцией ресурсов на уровне инстансов;
- профиль нагрузки, где один узел (например, эмбеддинг-воркеры) требует независимого масштабирования с отличным от остальных SLA;
- необходимость независимых релизов частей системы.
