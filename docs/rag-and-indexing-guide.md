# Как устроены индексация и RAG в VibeSolver

Это учебное руководство объясняет, как VibeSolver должен превращать исходный код, документацию и пользовательские сценарии в контекст для ответов на обращения. Оно описывает путь данных от файла до фрагмента, поиска и ответа. Три вида контекста строятся отдельно: код разбирается как программа, документация — как документ, User Flow — как структурированный сценарий.

## 1. Что такое RAG

RAG расшифровывается как Retrieval-Augmented Generation — генерация с поиском контекста. LLM не обязана помнить внутреннее устройство вашего продукта. Перед ответом система находит релевантные фрагменты из актуальных данных продукта, добавляет их к запросу и просит модель рассуждать с опорой на эти источники.

В упрощённом виде:

```text
вопрос → поиск доказательств → сбор контекста → LLM → ответ со ссылками
```

Индексация — подготовка данных для быстрого поиска. Индексация сама по себе не отвечает на вопрос и не обучает модель. Она создаёт структуры, которые позволяют отобрать подходящие фрагменты позднее.

## 2. Почему в VibeSolver три индекса

### Код

Код содержит исполняемую структуру: классы, методы, функции, типы и связи между ними. Кодовый chunker использует локально поставляемый пакет из 165 tree-sitter грамматик. В реестр включены Python, JavaScript/TypeScript, Rust, Go, Java/Kotlin, C/C++, C#, Ruby, PHP, Swift, Dart, Scala, Elixir, Erlang, Haskell, Lua, Perl, R, Julia, Clojure, Objective-C, Bash, PowerShell и другие языки. Для инфраструктуры добавлены YAML, JSON/JSONNet, TOML, HCL/Terraform, Bicep, INI/properties, Rego, Dockerfile, Make, CMake, SQL, GraphQL, Protocol Buffers, XML, CSS, HTML, Vue, Svelte и Astro. Парсер сохраняет цельные программные сущности там, где грамматика предоставляет подходящие AST-узлы, и привязывает фрагменты к файлу и строкам. Неизвестное расширение или отсутствующая грамматика индексируется как обычный текст; бинарные и слишком большие файлы пропускаются с диагностикой. Начальный pipeline сохраняет чанки, pgvector embeddings и полнотекстовое поле; поисковый API, RRF и reranker остаются следующей частью работы.

### Документация

Документы объясняют продукт на человеческом языке. Markdown разбивается по заголовкам, чтобы каждый фрагмент сохранял контекст раздела. Для PDF, DOCX, HTML и других форматов нужны отдельные извлекатели текста. Кодовый AST-парсер здесь не подходит: структура документов устроена иначе.

### User Flow

User Flow — пошаговый сценарий использования продукта: кто действует, какие шаги выполняет, что ожидает увидеть, какие части продукта участвуют и какие сбои возможны. Это помогает понять симптом в терминах пользовательского поведения и сузить поиск по коду и документации.

Flow хранится как версионируемая структура, а не как безымянный текстовый кусок. Для семантического поиска строится embedding из названия, шагов и режимов отказа, сохраняя ссылку на исходную утверждённую версию. Индексатор принимает JSON по строгой схеме с явным `approved: true`; интерфейс ручного утверждения ещё предстоит реализовать.

## 3. Путь файла до индекса

```text
источник
  → постоянный снимок в SeaweedFS
  → PostgreSQL-метаданные и content hash
  → специализированный parser/chunker
  → чанки и метаданные
  → embedding + полнотекстовое поле
  → активная версия индекса
```

SeaweedFS хранит исходные байты. PostgreSQL хранит описания файлов, пути, версии, чанки, статусы и ссылки на S3-объекты. Большие тела файлов не следует прятать в JSONB или в колонках таблиц индекса.

Для Git это особенно важно: временный клон нельзя считать постоянным хранилищем. Раньше импорт Git по умолчанию записывал в S3 только манифест, а не сами blob-байты. Теперь Git и legacy-стратегия `git_reference` сохраняют байты каждого файла по content-addressed ключам. PostgreSQL связывает файлы с неизменяемым снимком каждого запуска импорта; индексатор может загрузить его по ID снимка без повторного клонирования.

## 4. Что такое chunk

Chunk — небольшой смысловой фрагмент, который можно найти и передать модели. Слишком большой фрагмент расходует контекстное окно и содержит лишний текст. Слишком маленький теряет смысл и необходимые связи.

### Пример кода

```python
class ExportService:
    def build_csv(self, rows: list[Row]) -> bytes:
        ...
```

Для этого фрагмента полезны поля:

- `path`: `backend/export/service.py`;
- `symbol`: `ExportService.build_csv`;
- `start_line`, `end_line`;
- язык, репозиторий, commit и branch;
- родительский класс/модуль и content hash.

Если метод превышает лимит модели, его сначала делят по дочерним AST-узлам, например по внутренним функциям или крупным блокам, и только затем применяют ограниченное разбиение по токенам. При любом разбиении нужно сохранить исходные диапазоны строк.

### Пример документации

Заголовок `Экспорт / CSV / Права доступа` должен оставаться метаданными чанка. Если выкинуть заголовки при извлечении текста, фраза «роль должна иметь право export» потеряет смысловой контекст.

### Пример User Flow

Flow можно представить как одну сущность для семантического поиска плюс структурированные шаги. Отдельные шаги и компоненты не следует склеивать так, чтобы потерялись связи «действие → ожидаемый результат».

## 5. Embedding простыми словами

Embedding — список чисел, который модель получает из текста. Похожие по смыслу тексты обычно оказываются близко в этом пространстве. Запрос преобразуется той же embedding-моделью, затем поиск находит близкие векторы.

Это не понимание и не доказательство истинности. Например, embedding может найти близкий по смыслу фрагмент с устаревшим поведением. Поэтому важны версия источника, дата/commit, лексический поиск, reranker и проверка ссылок.

Размерность embedding — длина вектора. Векторы, созданные разными моделями или с разной размерностью, нельзя смешивать в одном логическом индексе без явного решения. В метаданных версии индекса нужно сохранять ID и revision embedding-модели и размерность. Замена модели требует новой версии индекса, а не тихого добавления новых векторов рядом со старыми. Для хранения векторов добавлена колонка pgvector; запуск индекса проверяет, что все ответы embedding-модели в партии имеют одинаковую размерность.

Embedding-клиент принимает локальные Ollama и FreeToken endpoint. Использовать облачную модель для исходного кода и проектных файлов запрещено, пока не появится проверенная схема обезличивания. `tree-sitter-language-pack==0.13.0` закреплён для воспроизводимой офлайн-поставки грамматик; пакет распространяется под MIT OR Apache-2.0, а отдельные включённые grammar имеют собственные permissive-лицензии (MIT, Apache-2.0, BSD и другие), перечисленные поставщиком. Перед распространением сборки нужно включать notices конкретных используемых грамматик. Обновление существующего `python-multipart` до `0.0.31` закрывает найденные `pip-audit` уязвимости; последняя проверка аудита после обновления показала отсутствие известных проблем.

## 6. Dense и лексический поиск

**Dense search** ищет близкие по смыслу фрагменты. Он полезен, если пользователь описал проблему другими словами, чем код или документация.

**BM25** ищет совпадающие слова, имена функций, коды ошибок, названия настроек и термины. В коде точные идентификаторы часто важнее смыслового сходства.

Оба поиска дополняют друг друга:

```text
запрос
  ├─ dense → кандидаты по смыслу
  └─ BM25  → кандидаты по точным словам
```

## 7. Объединение кандидатов и reranking

Dense и BM25 возвращают кандидатов с разными шкалами оценки. Их можно объединить Reciprocal Rank Fusion (RRF), которая использует позиции в списках, а не сравнивает несопоставимые сырые баллы. Упрощённый вклад документа с рангом `r` — `1 / (k + r)`; вклад суммируется по спискам.

После RRF система оставляет небольшой пул кандидатов. Cross-encoder reranker читает запрос и каждый кандидат совместно и оценивает их релевантность точнее, чем дешёвый предварительный поиск. Так дорогостоящая модель работает с десятками кандидатов, а не со всеми файлами.

## 8. Как проходит поиск по обращению

Пример: «У администратора экспорт CSV падает с ошибкой доступа».

1. Индекс User Flow ищет сценарии экспорта и известные режимы отказа.
2. Выбранный Flow указывает компоненты, связанные с экспортом и правами.
3. Поиск по коду запускается в этих компонентах; BM25 ищет конкретные `export`, `permission`, имена ролей и символы, dense-поиск — похожую логику.
4. Поиск по документации находит требования к роли и ограничения экспорта.
5. RRF и reranker сортируют кандидатов отдельно по типам, сохраняя источник каждого фрагмента.
6. Context Builder собирает компактный пакет с путями, строками, разделами и commit/version.
7. Агент делает вывод, указывая, какие данные его подтверждают и где есть неопределённость.

Flow здесь не заменяет поиск кода. Он помогает выбрать место, где искать. Это гипотеза для измерения: сравнить качество и стоимость поиска с Flow и без него.

## 9. Сборка контекста для LLM

Поисковая система может вернуть больше фрагментов, чем поместится в запрос. Context Builder должен:

1. отбрасывать дубликаты и устаревшие версии;
2. ограничивать число результатов каждого типа;
3. сохранять баланс кода, документации и Flow;
4. учитывать токенное окно конкретной модели;
5. добавлять короткие заголовки источников и точные ссылки;
6. не склеивать фрагменты разных файлов так, будто это один документ.

Иерархические сводки карты продукта могут помогать поиску на уровне модулей, но не должны подменять исходные доказательства. Если агент использует сгенерированное описание кода, provenance должен быть виден, а ссылка на исходные файлы — сохранена.

## 10. Генерация документации и User Flow

Генерация документации запускается только при актуальном code index. Она строит несколько поисковых запросов по разным аспектам: пользовательские возможности и API, бизнес-правила и состояния, данные и хранение, интеграции и фоновые задачи, ошибки и конфигурация, тесты и цепочки вызовов. Каждый запрос независимо ищет dense- и полнотекстовые кандидаты; RRF объединяет результаты, а context builder распределяет лимит между темами. Если документационный индекс актуален, он также участвует; локальные текстовые документы читаются напрямую и добавляются в контекст даже до индексации.

Генерация документации выполняется в два прохода той же выбранной моделью. Сначала модель делает функциональную выжимку по найденным чанкам и существующим файлам: возможности, действия пользователя, правила, изменения данных, связи компонентов, интеграции и сбои. Затем на основе выжимки и первичных фрагментов формирует новые Markdown-файлы. Выжимка помогает синтезировать информацию между фрагментами, но исходные чанки остаются доказательством; итоговые утверждения должны проверяться по ним. Лимит контекста распределяется между найденными темами и типами источников.

Генератор User Flow требует актуальные code и documentation индексы. Для каждого требуемого типа retrieval отдельно выбирает кандидатов по dense-векторам и полнотекстовому поиску, затем объединяет ранги через RRF. В LLM уходит ограниченный пакет найденных фрагментов с ID источника, путём и строками; весь индекс или репозиторий в prompt не копируется.

Пользователь выбирает чат-модель из подключённых в рабочем пространстве. Для Ollama используется `/api/chat`, для OpenAI-совместимых провайдеров — `/chat/completions`. При выборе облачного провайдера ему передаются найденные фрагменты кода и документации. Данные доступа к провайдеру и настройки проекта в prompt не включаются.

Ответ модели проходит строгую проверку: число файлов и их размер ограничены настройками `VIBESOLVER_MATERIAL_GENERATION_*`, пути проверяются на абсолютные компоненты и `..`, ссылки на источники должны соответствовать реально переданным фрагментам. Документация сохраняется как Markdown в локальном дереве вместе с provenance и перечнем источников. User Flow сохраняется как структурированный JSON-черновик с `approved=false`; до явного утверждения его нельзя включить в индекс.

Если целевой путь уже занят, новый материал получает свободное имя в той же папке, а существующий ресурс сохраняется без изменений. Ответ генератора допускает одну попытку исправления внешнего JSON. Для User Flow отдельно нормализуются распространённые варианты обёртки сценариев и названий полей; если обязательные шаги всё равно отсутствуют, выполняется одна попытка исправления сценария. После неудачи API сообщает об ошибке модели, не о конфликте индекса.

Текущий retrieval улучшает тематическое покрытие, но пока не строит явный граф вызовов между символами. Для решения issues полезно развить индекс до связей «маршрут → handler → use case → repository → модель/таблица», чтобы выдавать цепочку доказательств, а не только похожие по смыслу фрагменты.

## 11. Независимые статусы и готовность

Импорт сообщает, что сырой снимок получен и сохранён. Индексация сообщает, что из конкретной версии снимка построены поисковые артефакты. Это разные операции.

Для каждого индекса нужны состояния `not_started`, `queued`, `running`, `completed`, `failed`, `stale`. `stale` означает, что входные файлы, Flow, parser, chunker или embedding-модель изменились после построения.

Проект готов для Issues, только если обязательный импорт завершён, а code, documentation и user_flow индексы успешно построены для актуальных версий. При любой ошибке или устаревании индикатор красный, а интерфейс показывает конкретный следующий шаг. Генерация документации требует готового code index; генерация User Flow требует готовых code и documentation индексов. После генерации соответствующий индекс становится устаревшим и должен быть перестроен.

## 12. Обновление индекса

Для каждого файла вычисляется content hash. Если содержимое не изменилось и совпадают версии parser/chunker/модели, работу можно пропустить. Если изменился один документ, не нужно переэмбеддить все документы проекта.

Публикация должна быть атомарной:

```text
активная версия A остаётся доступной
  → строится версия B
  → проверяются число файлов и ошибок
  → указатель активной версии переключается на B
```

При ошибке B не должен заменить A частично. Если источник уже изменился, UI всё равно помечает A как устаревшую относительно источника, поэтому проект не выдаёт зелёный индикатор.

## 13. Как измерять качество

Понадобится размеченный набор запросов и правильных источников/фрагментов. Без него нельзя понять, улучшил ли новый chunker поиск.

- **Recall@k**: доля известных правильных фрагментов, попавших в первые `k` результатов.
- **Precision@k**: доля релевантных фрагментов среди первых `k`.
- **MRR**: насколько высоко оказался первый правильный результат.
- **nDCG**: качество ранжирования, учитывающее градации релевантности.
- **Groundedness**: подтверждаются ли утверждения ответа найденными источниками.
- **Answer correctness**: правильно ли решена задача, а не только найден похожий текст.
- **Latency и стоимость**: сколько занимает импорт, индексация и retrieval; сколько токенов идёт в модели.

RAGAS может помочь автоматизировать часть оценки, но автоматические оценки нужно сверять с экспертной разметкой. Для ВКР особенно полезна абляция: code+docs против code+docs+Flow, dense-only против dense+BM25, и разные стратегии чанкинга кода.

## 14. Частые ошибки

- Считать загрузку файла равной индексации.
- Сохранять Git-манифест и считать, что исходный текст доступен для повторного чанкинга.
- Разбивать код по одинаковому числу символов, разрывая функцию или теряя имя символа.
- Смешивать в одном индексе embeddings разных моделей.
- Принимать HTTP 200 от embedding API за доказательство качества retrieval.
- Искать только по векторам и терять точные имена функций и коды ошибок.
- Отдавать LLM много дублирующих чанков без источников и версий.
- Переиндексировать только часть снимка и незаметно сделать смешанную активную версию.
- Показывать проект готовым, когда один из обязательных индексов устарел или упал.

## 15. План реализации в VibeSolver

1. Зафиксировать сырые файлы Git и связать их с версиями источника.
2. Добавить run/state-модель трёх индексов и active version.
3. Реализовать tree-sitter кодовый pipeline и диагностику неподдерживаемых языков.
4. Реализовать документационные parser adapters и заголовочный chunker Markdown.
5. Зафиксировать схему User Flow, approval и flow embeddings.
6. Добавить API и UI для трёх отдельных операций, прогресса и повторного запуска.
7. Отключить генерацию без требуемого актуального индекса.
8. Включить красно-зелёную готовность и блокировку Issues.
9. Добавить поиск по трём индексам, RRF/reranking и оценивание на golden set.
